# 方案：「一键发布」场景路由与方案自评（完善版）

> 本方案汇总 2026-08-15 协商会话中「一键发布（publish）」模式从需求、设计、实测到修正的全部结论，
> 明确每项调整的依据（实测驱动）、具体改进点与剩余实施步骤。当前为方案稿（待确认实施）。

---

## 一、背景与目标

**需求**：新增「一键发布」模式——输入粗略想法（如「我想开发一个纸牌游戏」），一键生成完整可实施的开发规格（目标/数据结构/核心机制/交互/技术方案/实施路线/验收清单），多轮补充可逐步细化。

**目标形态**：模糊想法 → 场景自动路由（游戏/软件/通用）→ 九章规格生成（网络检索 + 工作区参考）→ **方案自评判定**（保留/调整）→ 多轮扩充闭环。

## 四、待实施改进点

### 改进点 1：场景自动路由（方案 C）

1. **`detectScenario(text, keywords)` 纯函数**（PURE 区段，可单测）：
   - 游戏词表：游戏/玩法/关卡/角色/战斗/卡牌/塔防/肉鸽/roguelike/Boss/副本/抽卡/回合/射击/模拟经营/放置/解谜/剧情/成就/装备/技能/地图…
   - 软件词表：软件/应用/系统/平台/SaaS/Web/网站/工具/API/后端/前端/数据库/微服务/管理/协作/自动化/脚本/插件/客户端/App/移动端/桌面…
   - 计分制（命中词计数，多者胜；平局/双零 → generic），返回 `game | software | generic`
2. **system 场景引导**：检测结果显式注入 system——「本次场景判定：game/software」+ 场景适配指令（文案内置 publish.md「场景适配」段为事实源）：
   - game：三、数值与经济按数值表/经济公式展开；五、核心机制含玩法系统
   - software：三、数值与经济改性能指标与容量约束；五、核心机制改核心功能与业务规则；补充数据流与 API 设计
   - generic：默认九章（不追加）
3. **检索词场景化**：`buildWebQuery` 结果追加场景词（game → 游戏实现；software → 软件架构）
4. **日志**：`scenario=game/software/generic`
5. 生效条件：publish 模式 + 预算>0（检索路径）；generic 兜底不阻断

### 改进点 2：方案自评判定（优化侧模型自执行）

publish.md 追加【方案自评判定】段（第十部分附录，不改变九章框架）：

```
【方案自评判定】（输出规格后必须追加，不改变九章框架）
一、一致性核对：用户已明确需求逐条是否都有章节覆盖？缺项列出。
二、完整性核对：九章是否全部展开？缺章列出。
三、可实施性核对：是否存在未标注「默认」的设计空白？列出。
四、判定结论：【保留】（全部通过，可开工）或【调整】（列出差距项
   + 调整方向，并在「调整建议」小节给出 ≤5 条修订要点）。
输出格式：【方案自评】- 一致性/完整性/可实施性 - 结论 - 调整建议
锚点规则（防自嗨）：任一「用户明确需求未覆盖」或「九章缺章」→ 必须判【调整】。
```

- 自评为【调整】→ 调整方向供用户下一轮补充（记忆链）→ 再自评 → 闭环
- 多轮衔接：自评块随规格输出，用户可据此修改草稿后继续优化

## 六、风险与回退

| 风险 | 应对 |
|---|---|
| 词表误判（"游戏"出现在软件描述） | 计分制 + generic 兜底；词表按实测扩充 |
| LLM 自评流于形式（自嗨） | 锚点规则强制（缺需求/缺章必须判调整）；实测验证判【调整】场景 |
| 自评段增加输出长度 | publish 已不设输出限制 ✅ |
| 路由/自评行为异常 | 改动集中在 publish 路径（system 注入 + 纯函数）；移除注入即回退当前行为，不影响其他模式 |
